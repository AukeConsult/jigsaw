# Canvas – project guide

Canvas lets a person make a canvas area of a chosen size in pixels (with a grid), make **canvas objects** (figures and arrow connectors) with their own
size, border, colours and font, and put copies of them on a canvas: move them, resize them, fasten arrows to figures, group them. Everything saves by
itself. Built on the same structure as Seven Friends.

## Structure
- `frontend/` – Angular 20 (standalone components, signals, Bootstrap 5 + SCSS, Transloco), hosted on Firebase Hosting site `canvas-auke` (target `canvas`).
- `functions/` – Node 22 + TypeScript Express backend, deployed as the Cloud Function `canvasApi` (served at `/api/**`), codebase `canvas`.
- `functions/src/models/shared/` – **the model, the ONE place to edit shared code.** `scripts/sync-models.mjs` copies it to `frontend/src/app/models/shared/` (generated, gitignored, never edit that copy). Shared files may only import from each other.
- `client-wrappers/android` – Capacitor Android shell, generated with `npm --prefix frontend run cap -- add android` (not generated yet).

### The model (`functions/src/models/shared/`)
| file | what is in it |
|---|---|
| `canvas-object.ts` | a canvas object's settings and the classes `CanvasBaseObject` (parent) → `CanvasFigure` → `CanvasArrow` |
| `geometry.ts` | `Point`, `Box`, resize handles and `resizedBox`, and `SmoothCurve` (the curve of a bent arrow; used by the model and by the drawing). No knowledge of objects |
| `placed.ts` | an object placed on a canvas: `PlacedBase` → `PlacedFigure`, `PlacedArrow` |
| `diagram.ts` | `CanvasDiagram`: what the placed objects do together (snap, follow, resize as a group, layers) |
| `canvas.ts` | a saved canvas (`CanvasSpec`) and `CanvasArea`, which checks one |

### The two modules and their routes
The app has two modules. Each is a route tree that is loaded when it is first opened (`loadChildren` in `app.routes.ts`), has its own shell with its own header menu, and the root (`app.ts`) only holds the router outlet.
- **`/jigsaw` — Karins jigsaw** (`app/jigsaw/`: `jigsaw-shell.ts`, `jigsaw.routes.ts`). **The default: `/` goes to `/jigsaw`**, and so does any address that is not known. Its header menu has the brand "Karins jigsaw", the page link, and a small link to the canvas module.
- **`/canvas` — Canvas** (`app/canvas/`: `canvas-shell.ts`, `canvas.routes.ts`). For other purposes and for testing. Its header menu has the brand "Canvas", "Canvas area" (`/canvas`), "Objects" (`/canvas/objects`), and a small link to the jigsaw. `/objects`, where the objects page was before there were modules, goes to `/canvas/objects`.
The two modules share the pages and the parts under `app/` (`home/`, `canvas-board/`, ...) and the model; a module's route says how the shared canvas page is set up (the route data, see below). A new page of a module goes in that module's routes file; a rule that is only for one module is set in its route data, not by an `if` on the address.

### The frontend (`frontend/src/app/`)
One folder for each module, and what both use:
- `canvas/` – the **canvas module** (`/canvas`): `canvas-shell.ts` (its header menu) and `canvas.routes.ts`, and all the canvas components. `home/` is the canvas page: it holds the open canvas, autosaves, opens/starts/deletes saved canvases, and is also the page of the jigsaw module (set up by its route data). It has three parts: `canvas-panel/` (settings + saved list), `canvas-board/` (the canvas, its objects and all pointer tools) and `object-palette/` (objects to drag in). `objects/` is the Objects page, with `object-panel/` (the form) and `canvas-shape/` (draws an object as SVG). Also `canvas-list.service.ts`, `canvas-objects.service.ts` (the API) and `drag.ts`.
- `jigsaw/` – the **jigsaw module** (`/jigsaw`, Karins jigsaw): `jigsaw-shell.ts` (its header menu) and `jigsaw.routes.ts`, and everything only the jigsaw uses: `puzzle-piece/` (draws a piece), `picture-cropper/` (finds the cut of a picture), `fit-picture.ts` (cuts the picture to the canvas shape), `piece-graphics.ts` (draws the graphic of each piece), `piece-sync.ts` (keeps the pieces in the database) and the API services `jigsaw.service.ts`, `jigsaw-image.service.ts`, `jigsaw-pieces.service.ts`.
- `core/` – what both modules use: `autosave.ts` (saves a change a pause after it), `api-collection.ts` (the base of the API services), `session-storage.ts` (choices kept for the session: `readSession`, `writeSession`, `isBoolean`), `theme.ts` (`cssVar`, `cssNumber`, `isWideScreen`: canvas code reads colours and sizes from the look) and the Transloco files.
- `src/styles.scss` – **the one place for the look**: fonts, colours, sizes, layers and every custom class, as `--app-*` tokens on `:root` (Bootstrap's own variables are set from them) and responsive rules (`from`, `below`, `touch` mixins; breakpoints `$bp-*`). Components use Bootstrap classes and the classes/tokens of this file: no hard-coded colour, font or size in a template, an SVG attribute, canvas code or a component `styles:` (the colours of objects the person made are data and the only exception). Canvas code reads tokens with `cssVar`/`cssNumber`.
- `models/shared/` – the model (generated copy, never edited).
- A module's folder holds its own things. The canvas page (`canvas/home`, `canvas-board`, `canvas-panel`) is shared by the two modules, so it knows a little of the jigsaw (the pieces, the helper banner, the sidebar) and imports from `jigsaw/`; the jigsaw module in turn opens the canvas page. Anything new that only one module uses goes in that module's folder.
- Backend: `canvas-list.ts` / `canvas-objects.ts` (the routes: they only check, call `stored()` and the store), `document-store.ts` (the Firestore code both use: list, add, replace, delete).

## Rules for the code
1. **Classes work on their own object.** A rule belongs on the class that owns the data, at the right level of the parent/child hierarchy: what every object has is on `CanvasBaseObject`, what a figure adds on `CanvasFigure`, what an arrow adds on `CanvasArrow` (an arrow *is a* figure, a figure *is a* base object). Children override small hooks instead of `if (kind === …)` branches. Placed objects know their own geometry; the diagram does what they do together.
2. **Model objects never change.** Moving, resizing or any other change gives a new object (or a new diagram, or the same one when nothing changed). Components keep the plain stored data in a signal and make the classes from it when they need them (`CanvasDiagram.from(...)`).
3. **Components are thin.** A component turns what the person does into calls on the model classes and shows the result. Business rules do not live in components or in the routes.
4. **What is stored is decided by the model.** `X.stored(...)` says which fields are saved (only the known ones); `X.fromStored(...)` reads a document that an older version saved and gives it what it lacked. Routes only call them. Never save a field that is not known.
5. **One validation, used everywhere.** `error()` on the classes (`CanvasBaseObject.of(data).error()`, `CanvasArea(...).error()`) is used by the forms, the page and the API, so they cannot disagree.
6. Keep files small and about one thing; no unused code (check with `tsc --noUnusedLocals`); comments say *why* in plain words.
7. Always use Bootstrap in pages; custom CSS only if absolutely necessary, and then in `styles.scss` (inline styles only where a value is computed, such as a position or size from the data).
8. Never edit anything in a `lib/` or `dist/` directory (compiled output): edit the `.ts` source and rebuild.
9. Do not guess when debugging: establish the mechanism (exact line/condition) before fixing; if it is not found, ask for evidence.
10. **Stored pixels, drawn at a scale.** Sizes and positions in the data are stored pixels and never depend on the screen. The board draws the pieces area at `scale` (`canvas-board.ts`: the picture and the space round it fitted to the room, whole and in proportion, at most 1, at least 0.1), and every pointer position is turned back with `/ scale()` before it reaches the model. The store frame is beside the picture, or below it on a screen narrower than `--app-store-below` (1200 px, `stacked`); this is only how it is drawn: the store is then a short strip (`STACKED_STORE_ROWS` grid steps high) that scrolls sideways only, the tall store cut into bands side by side; `place()` and `areaPoint()` map between a stored place and its place in the strip. Beside the picture the frame scrolls up and down only: a store wider than the frame is shown in slices one under the other (`sliceCount`), the same kind of mapping. The stored coordinates of the pieces never change. New pointer code must do the same; the handles divide their size by `--app-scale` so they stay finger-sized.
11. **Small screens.** Below 1200 px (`--app-sidebar-fold`, `$bp-xl`) the jigsaw sidebar is folded behind a bar (name and "Matched x of y") above the board and opens over it; the choice is kept in the session as `jigsaw.sidebarOpen`.

## Rules for what the app does
- **Canvas:** a name, width and height (whole pixels), a grid (pixels between points, 0 = off, shown or hidden). The canvas itself is layer 0.
- **Objects** (collection `canvas-objects`): a *figure* (square, circle, triangle, histogram) with a default size, border, corner radius, colours and font; or a *connector* (an arrow, one way or both ways, solid or hollow). A square and a circle have equal sides.
- **Placed objects** are independent copies stored inside the canvas document (`placed`), so changing or deleting the original does not change a canvas.
- **Position:** a placed object's *centre* is what sticks to a grid point. Everything stays inside the canvas.
- **Connection points:** a figure has 8 on its border (a triangle 6); an arrow has 2, one at each end (`start`, `end`). An arrow has three more points that shape it (not connection points): a quarter, half and three quarters of the way along. Drag each sideways on its own to curve the arrow, even into an S (`bendStart`, `bend`, `bendEnd`, in pixels from the straight line; all three 3 px or less is straight; a plain `bend` makes the other two follow at three quarters of it); drag back to the line to straighten. An arrow end within 24 px of a figure point snaps to it exactly and is fastened (and the other way: a figure near a free arrow end). Fastened points are drawn as a point in a point.
- **Arrows follow:** a fastened arrow follows its figure when it moves or is resized; the other end stays. Removing a figure frees its arrows. Grabbing an arrow near an end moves that end alone; the two handles on its sides change its width across.
- **Layers:** the canvas is layer 0; objects are on layers 1–1000, the first on 10; a new object goes on the last (highest) layer in use; a higher layer is in front.
- **Resizing:** one figure by its 8 handles (opposite edge stays, edge on the grid, square/circle stay equal-sided, at least 4 px). A group (drag a rectangle on the empty canvas): positions scale by the group box on each axis, every figure keeps its shape and scales by the factor that changed more; an arrow is stretched by its ends and its thickness scales the same way.
- **Delete** (or Backspace, when not typing in a field) removes the picked objects.
- **Saving:** every change saves by itself a pause later (autosave); nothing is saved while the settings are not allowed. A saved change **replaces the whole document** (only the creation time is kept), so nothing removed or stale is left in the database.

## Shared Firebase project (IMPORTANT)
The Firebase project `sevenfriends` is shared with Seven Friends. Therefore:
- Deploy only `hosting:canvas` and `functions:canvas` (the npm `deploy*` scripts do). Never `firebase deploy` everything, and never deploy `firestore`/`storage` rules or indexes from here: that would overwrite Seven Friends' live ones. `firestore.rules` and `storage.rules` here are for the emulator only. Change live rules/indexes from the Seven Friends repo.
- The functions codebase is `canvas`, not `default`, so a deploy here never deletes Seven Friends' functions.
- Collections and Storage paths start with `canvas` so they cannot collide with Seven Friends' data.
- Do not run any `firebase` command that changes the shared project, and do not deploy, commit or push, unless asked.

## Running and testing
- `npm run install:all`, then `npm run dev` (functions watch + emulators + frontend). The frontend is on **http://localhost:4210**; emulator ports are offset from Seven Friends (UI 4010, Functions 5011, Firestore 8090, Auth 9109, Storage 9209, Hosting 5010) so both can run together.
- `npm test` runs the backend tests (Vitest). `npm run test:emulator` starts a Firestore emulator (test ports, not the dev ones) and runs the real stores against it (`functions/test-emulator/`). The model has the real tests: every rule above is tested on the classes (`functions/test/`), the Firestore code with a small fake collection. A rule is not done until it has a test.
- `npm run build` builds both. The frontend build also copies the model (`sync:models`).
- The frontend has no unit tests: check pages in the browser (the dev server must be the current one; restart it if the page shows old code).

Longer documentation is in `docs/guide/` (user guide, model, API and running).

## Jigsaw page ("jcanvas")
The jigsaw module's page (`/jigsaw`) is called **Karins jigsaw** (the menu link, the title of the browser tab and the title at the top of its sidebar; the address `/jigsaw`, the collection `jigsaw` and the names in the code stay as they are). It is the canvas page on its own collection; the jigsaw canvas is called **jcanvas**. It is the same `Home` component, set by the route data in `app.routes.ts` (`heading`, `collection`, `gridInset`, `numberPoints`, `palette`, `background`, `tools`, `fillScreen`, `sidebar`), so a rule for the canvas page holds for jcanvas unless it says otherwise.
- Stored in the Firestore collection `jigsaw` through `/api/jigsaw` (same checks and shape as `canvas-list`; `JIGSAW` in the model, `JigsawService` in the frontend).
- **Where a jigsaw is kept:** its settings and its non-piece objects are the Firestore document `jigsaw/<id>` (collection `jigsaw`, `/api/jigsaw`). **Each piece is a document of its own** in the subcollection `jigsaw/<id>/pieces/<piece id>` (`JIGSAW_PIECES`, `JigsawPiece` in the model, `functions/src/jigsaw-pieces.ts`) with its `number` (the grid point it belongs on: row × columns + column + 1), `col`, `row`, its four edges, `size`, where it is (`centerX`, `centerY`), its `layer` and **`matched`** (it lies on its own place: the server works this out from where the piece is, `JigsawPieces.matched`, whatever the page says). The page does not put the pieces in the jigsaw document (`placed` there holds only what is not a piece). The background picture and the **graphics of the pieces are files in Firebase Storage**, `jigsaw/<id>/picture` and `jigsaw/<id>/pieces/<piece id>`.
- **Files go through the API, never from the page to Storage** (the way Seven Friends keeps its files): the page sends bytes to the API, the Cloud Function writes them with `firebase-admin` (`getStorage().bucket()`; the Admin SDK ignores the storage rules, which let nobody in, so the rules are not touched), the type is found from the first bytes (never from what the page says) and a file is read back through the API. The routes: `PUT/GET/HEAD/DELETE /api/jigsaw-image/:id` (the picture: the raw bytes as the body, jpeg, png or webp, **at most about 5 MB**, 404 when there is no such jigsaw) and `/api/jigsaw-pieces/:id` (`GET` the pieces without graphics; `PUT {pieces: [...with `graphic`: a data address of a png, webp or jpeg of at most 150 KB]}` when the jigsaw is cut: all the pieces and graphics are replaced; `PATCH {moves: [{id, centerX, centerY, layer}]}` where pieces are now; `GET .../graphic/:pieceId`; `DELETE`). Deleting a jigsaw takes away its pieces, their graphics and its picture.
- **Saving the game and reinstating it:** a cut sends all the pieces with their graphics (drawn in the page from the picture, `jigsaw/piece-graphics.ts`, a webp of each piece with its tabs); after that `PieceSync` (`jigsaw/piece-sync.ts`) saves only the pieces that were moved, a pause (0.8 s) after the last move, and the server sets `matched`. Opening a saved jigsaw reads its pieces back (`Home.loadPieces`): each is where it was left, on its layer, with its edges and number, and the sidebar shows **Matched: x of y** (and a progress bar; "solved!" when all are). A matched piece is drawn with a green outline. A jigsaw that an older version saved with its pieces in its own document has them moved to the subcollection when it is opened.
- **Background picture** (jcanvas only): a jpeg, png or webp chosen in the panel, shown behind the grid points and objects and covering the canvas (not once it is cut: see below). Before it is saved the page **cuts it to the shape of the canvas** (width : height). Choosing a file opens `app-picture-cropper`: the picture lies behind a frame with the shape of the canvas and is dragged (and zoomed, slider or wheel, up to 4 times) to find the cut; "Use this cut" gives the part of the picture the frame shows (`PictureCrop` in the model: it never lets the frame show what is outside the picture), Cancel keeps the old picture. `fitPicture` (`jigsaw/fit-picture.ts`) makes a jpeg of that part, up to twice the size of the canvas and at most about 5 MB (`MAX_PICTURE_BYTES`). What is saved, what the pieces show and what the helper picture shows is that cut picture, so the helper picture has the shape of the canvas. If the width or height of the canvas is changed later the picture is not cut again (choose it again). A new jcanvas is saved when a picture is chosen, since the picture belongs to its id.
- **Helper banner and hidden picture:** once the picture is cut into pieces (the canvas has pieces) the picture is no longer shown behind the canvas (`backdrop` of the board: it is derived, nothing is stored; the pieces still show their parts of it). Above the jigsaw pieces area there is a one-line helper banner (`helperBanner` of the board) with a switch, "Helper picture" (on to begin with, not saved). When it is on, the whole picture is shown in a frame that floats on top of the rest of the page (`position-fixed`): it is moved by its title (`helperFrame`, kept on the window; the pointer is captured by the title, which is not redrawn), sized by its corner (`helperScale`: a quarter of the picture's width and height to begin with, from a tenth up to a half, the picture keeps its shape) and closed with its x (which turns the switch off).
- **The frame around the picture area is a setting of the jigsaw** (`CanvasSpec.frameWidth`, a whole number of pixels from 0, no frame, to 20, `CanvasArea.MAX_FRAME_WIDTH`; 4, a frame that can be seen, when a jigsaw has none, `CanvasArea.DEFAULT_FRAME_WIDTH`): it is set when the jigsaw is made ("Frame (px)" on the page for a new jigsaw) and drawn by the board (`frameWidth`) as a blue line (`outline`, outside the picture area, so it takes no room and nothing placed moves). The page for playing keeps it when it saves the jigsaw (a field that is left out of a save is gone, since a save replaces the whole document).
- **The helper choices stay for the session** (`core/session-storage.ts`, `sessionStorage`: kept when the page is reloaded or left and come back to in the same browser tab, gone when the tab is closed; no storage, or a value that is not what it should be, means the board starts as if nothing was kept): the two switches ("Helper picture", "Only corner and edge pieces") and the place and the size of the helper picture frame (`jigsaw.helper`, `jigsaw.edgesOnly`, `jigsaw.helperFrame`, `jigsaw.helperScale`). They are not saved in the database; the Debug button is not kept.
- **The pieces are drawn in a layer of their own, on top of both frames** (the board's `overlay` and `place()`): with a store, every piece is drawn in one layer that lies over the canvas and over the store frame, and not inside either, so a piece is never cut off or put under a frame, also when it lies over the edge of one (a group of pieces that stick together can lie over the canvas and the store). The layer is as big as the whole area (so it scrolls with it), takes no room, lets the pointer through except at the pieces, and is above the frames (`z-index: 1`; the handles and the picking frame are above it). A piece of the store is put where the store frame shows it (the board follows how far the frame is scrolled, `storeScroll`), is cut off only at the top and bottom of the frame (`clip-path`, not at the sides), and is left out when it has been scrolled out of sight. Without a store (the canvas page) the objects lie in the canvas as before. The frame itself is only the scrolling background and the place a frame is dragged on to pick pieces.
- **Helper: Collect pieces:** a button in the helper banner puts the pieces that lie in the scrolling store frame together at the top of it (`CanvasDiagram.collectPieces`, called by the board with the pieces in the store that are shown: with "only corner and edge pieces" on, the hidden ones are not collected). They are packed in rows from the top left of the frame (`COLLECT_MARGIN` from the top and the sides, `COLLECT_GAP` between, both shares of the size of a piece), in the order they were lying: from the top down, and in a row from left to right; a row that is full starts the next one. Pieces that stick together are put as one block and keep their places in relation to each other; a group that has a piece outside the store (or hidden) is not collected. The frame is scrolled to its top. It changes only places (they are saved like any move of pieces); the button is disabled when there is nothing in the store.
- **Helper: only corner and edge pieces:** a second switch in the helper banner, "Only corner and edge pieces" (off to begin with, not saved; disabled when there are no pieces), hides the pieces from the inside of the picture, so the border can be put together first. A border piece is one with a flat side (`JigsawPieces.isBorder`: a corner has two, an edge piece one), which is every piece with `col` or `row` on the border of the picture. What is hidden is only not drawn: it stays where it is, is saved as before, and is not picked by a frame dragged over it (`hiddenIds` of the board). The banner tells how many are shown of how many.
- **Jigsaw pieces** (`functions/src/models/shared/jigsaw.ts`, `JigsawCut`): "Cut into pieces" in the panel (when the jcanvas has a picture) replaces what is on the canvas with one piece for each whole cell of the grid (at most 500 per canvas, so use a bigger grid for a big canvas). A piece is an ordinary placed square figure of grid × grid pixels with `piece` (`col`, `row` and its four edges: 1 tab, -1 blank, 0 flat on the border); a piece is allowed only on a figure (an arrow cannot be one) and has no resize handles. Every inner edge is a tab on one piece and the matching blank on the other, chosen by chance. The pieces start scattered in the store frame (`JigsawCut.scatter`: in rows, with a random space between neighbours across and down from a little overlap (-0.3 of a piece) to 0.8 of a piece, `PIECE_GAP_MIN`, `PIECE_GAP_MAX`, so pieces can lie partly over each other, and each on a random layer; the store is made as wide as the pieces need). **Reset** (next to Cut into pieces, when there are pieces) shuffles all the pieces again (`JigsawCut.reshuffle`: new places and layers in the store frame, the same edges; what is not a piece stays). `app-puzzle-piece` draws a piece: its outline (`JigsawCut.path`, the tabs reach outside its square) cut out of the picture, which covers the whole canvas, so a piece shows its own cell of it wherever it lies; a matched piece has a green outline. The number of the grid point a piece belongs on is drawn on it only when **debug** is on.
- **Pieces that stick together form a group** (`CanvasDiagram.stuckGroup`): two pieces stick when they are neighbours in the picture (next to each other, or one over the other) and lie exactly where they belong in relation to each other (one piece apart; places are whole or half pixels, so it is exact, `STICK_TOLERANCE_PX`); a piece sticks to what its neighbour sticks to, so it is a whole group. **Nothing is stored for a group: it follows from where the pieces are**, so a saved jigsaw that is opened has the same groups, and the saving of piece places (`PieceSync`) is all it needs. Picking up a piece takes its whole group with it (`moveGroup`; the board works out the pieces that move, `moving.ids`, when it is picked up); a picked frame of pieces takes the groups of all of them. **Shift** while picking up a piece takes that piece alone, which pulls it loose. **Dropping** (`CanvasDiagram.dropPieces`) is where pieces stick: a group that is dropped within the snap range (`snapPercent`, the same setting as for clicking into place: 0 means nothing sticks) of its own grid point, or of the place where one of its pieces fits a neighbour that is not in the group, moves by the smallest of those steps, so that piece is exactly there, and the groups that now fit each other are one group. It clicks exactly or not at all: when the area has no room for the whole step the group stays where it was dropped. The pieces that joined, and the one that was dropped, blink and the device vibrates. Reset scatters all the pieces, which breaks every group.
- **Playing:** a piece is moved in steps 50 times smaller than the grid (`PIECE_STEP_DIVISOR`, made a whole number of half pixels, since the server only takes a whole or a half pixel for the place of a piece, and not finer than half a pixel), not from grid point to grid point, and it does not snap while it is moved. A piece that is picked up goes to the front (`CanvasDiagram.bringToFront`: a layer above all the others) and stays there when it is dropped. **Several pieces can be picked and moved at once**: drag a frame on the empty canvas or the empty store frame (it works in both), then drag any picked piece and all move by the same amount (`CanvasDiagram.moveGroup`: half pixels, as far as all stay inside the area; a group keeps its order when it goes to the front). **A piece clicks into place only when it is dropped** within a range of its own grid point (its home, `PlacedFigure.home()`, the centre of its cell of the picture): it goes exactly there (`CanvasDiagram.dropPieces`, called by the board when what is moved is let go), **blinks** (swells, shakes and shines for 0.7 s: the animation is the small CSS of `app-puzzle-piece`, kept to this) and the device **vibrates** (`navigator.vibrate`, where it can). **How close it has to be is a game parameter, `snapPercent`**, a percent of the grid size, saved with the jigsaw document (`CanvasSpec.snapPercent`, a whole number from 0 to 100, where 0 means a piece never clicks; 50, half a grid step, when the jigsaw has none, `CanvasArea.DEFAULT_SNAP_PERCENT`; `CanvasArea.snapRangePx` makes pixels of it), set in the sidebar ("Snap range (% of the grid)"). Pieces that are in place when a jigsaw is opened or shuffled do not blink, nor do pieces that were in place when they were picked up. A piece in place can be moved away again. Moves that wait for the 0.8 s pause are sent at once when the page is closed or hidden (`PieceSync.leaving`, a `keepalive` request), so the game is as it was left.
- **The store frame and the jigsaw pieces area (jpa):** a jcanvas that has been cut has a `storeWidth` (saved with it, `CanvasArea.storeFrame`): a frame beside the canvas, one grid step from its right edge, `STORE_HEIGHT_FACTOR` (3) times the height of the canvas high, scrolling up and down. The cut puts the pieces in it, scattered (see below). The canvas and the frame together are the jpa, where a piece can be moved anywhere: all of it is one coordinate area (`CanvasArea.extent`, used by the board, the page and the API to check that every object fits), and a piece with its centre right of the canvas is drawn in the frame. While a piece is moved the pointer is held by the whole board, not by the piece, since the piece is drawn again when it changes place; over the frame the pointer position is the frame's (scroll included), elsewhere it is on the part of the jpa left of the frame, and not outside what the area shows. A piece can be moved anywhere on the jpa: on the picture, in the blank space under the picture (as far down as the area shows) and in the store frame. A piece has no resize handles.
- **A jigsaw is given a number of pieces, not a grid size:** the sidebar asks for "Pieces" (2 to 500) and tells the grid size that follows (`Home.relayout`, `JigsawCut.layoutFor`): the pieces are square, a piece is about the square root of (width × height / pieces) on a side, the grid size that gives the number of pieces nearest to the one asked for is taken, and the canvas is made a whole number of pieces wide and high (so the number can come out a few more or fewer, and the box shows the number that really comes out). It is worked out again when the width, the height or the number of pieces is changed (when the field is left), always from the size the person typed (`askedSize`), not from the size the canvas was made last time, so asking for other numbers of pieces and back gives the same canvas again. The grid size is still what is saved (`gridSize`); the number of pieces shown on opening is columns × rows. Pieces that are already cut keep the size they were cut with until the picture is cut again.
- The grid of a new canvas or jcanvas is 50 px (older documents without a grid read as 5 px).

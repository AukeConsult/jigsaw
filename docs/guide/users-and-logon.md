# Users, signing in with Firebase, and language

Part of the project guide (moved out of `CLAUDE.md`; text unchanged). Read this before changing this area.

## Logon and access: the rules on one page
Who may do what with a jigsaw is in the table "Who may do what with a jigsaw" at the end of `jigsaws-and-sharing.md`. This is who may do what with an **account**, and how the server knows who asks. The server decides all of it (`functions/src/logons/gate.ts`, `functions/src/jigsaw/app.ts`, `user-levels.ts`); the page only shows what the server allows.

**1. Who asks.** Every call says who acts with the header `X-Jigsaw-User` (the id of the jigsaw account that plays) and, when somebody is signed in, `Authorization: Bearer <Firebase ID token>`. An account with **no verified login** is open: whoever knows its id may act as it, so nothing that matters is allowed to depend on it (see 3). An account **with** a verified login (up to 7, `LOGONS_MAX`) is used only by somebody signed in with one of them.

**2. The gate** (`createGate`, in front of the whole API), for the account the call acts as (the header, and the account in the address of `/jigsaw-users/:id/...`):

| the call | answer |
|---|---|
| the account needs no login | goes through |
| the token is one of the account's logins | goes through |
| only looking (a read that is not about the account: the lists, a jigsaw, a picture) and no good token | goes through **for nobody** (the header is taken off), no login asked |
| no token, or a bad one | **401** `logon-required` |
| a good token, but not one of the account's | **403** `wrong-logon` |
| Firebase cannot be asked | **503**, never a way through |
| the login that comes is verified for an account that is a real admin (`isAdminLogin`) | goes through **as any account, on every call and every item**, except the logins of an account |

The gate keeps an account 10 seconds (`USER_KEEP_MS`) so each call is not a read; **a change of its logins or of its level makes it read again at once** (`Gate.forget`: the logon routes, and `PUT /jigsaw-levels/:id` through `Logons.forget`), so an account that has just become an admin is not refused as what it was. Tested in `user-levels.test.ts` ("an account that has just been made an admin") and on the real Firestore in `test-emulator/stores.emulator.test.ts`.

**3. Levels (user, publisher, admin).** Kept on the account (`level`; nothing kept means user). **A level counts only for an account with a verified login** (`UserLevels.of`): an account with none is always a user, cannot be given a higher level (409), and an account that loses its last login loses its level. Never set by a body that makes or changes an account. What each may do: a **user** plays and makes private or hidden jigsaws; a **publisher** also makes jigsaws public; an **admin** also changes and deletes any jigsaw and round, opens private and hidden jigsaws by their address, starts a round on a private one, changes and deletes the accounts of others (never their logins, never the last admin), and sets levels. An admin does **not** find another's private jigsaw on the home page or in the lists.

**For now an admin is checked on the jigsaw account only** (its level, and a verified login). A second mark on the user itself, in the login's record `user-account/<uid>` (a field owned by the jigsaw, added **by hand** in the document for now, since Seven Friends has no user admin page yet), so that both must say admin, is decided and not built yet; the jigsaw would only read it, never write it (`TODO.md`, "A second mark for an admin").

**4. Setting levels, and the first admin.** `PUT /jigsaw-levels/:id {level}` (not under `/jigsaw-users/:id`, so the gate asks for the login of the one who asks, not of the account that changes): an admin only, **except while there is no admin at all** (`GET /jigsaw-levels/open` says `{open: true}`): then any account that exists may, so the first admin is made from the admin page `/jigsaw` (the entry Admin of the app's account menu is then there for every account that plays, and for admins otherwise). The last admin cannot step down (409). Nothing about the first admin is by hand any more.

**5. An admin acts as any account, with nothing but the admin's own login.** There is no extra key and nothing is stored: the key is the **Bearer token** that every call already carries. The gate asks the database (`linkedTo`) whether that login is verified for an account that is a real admin (it needs a login, and has the level: `UserLevels.of`). If it is, the call is answered as the account named in `X-Jigsaw-User` (or in the address), without the login of that account, and **every level question for the whole call is answered admin** (`res.locals.byAdmin`, `intoAccount`, an `AsyncLocalStorage` for that call only), so the admin login is accepted on every call and on every item, also a call that names no account. The button that goes into an account on `/jigsaw` (`JigsawUserService.openAs`) only makes the page play as the account, and opens `/play/account`; it writes nothing. Not for `/jigsaw-users/:id/logons`: the logins of an account stay its own. The page knows the login is an admin's from the session: `GET`/`POST /session` tell each account the login is verified for with its `level` (`LinkedUser.level`), and `JigsawUserService.admin` is worked out from that each time (an admin login, and an account plays that the login is **not** verified for). **Another account of the admin's own login is the person's own account, not going into somebody else's: it has its own level (a plain user, if that is what it is), there is no warning bar, and the gate does not give that call admin rights** (`byAdmin` only for the admin's own account, an account the login is not verified for, or a call that names no account; tested in `user-levels.test.ts`, "another account of an admin's own login"). A warning band (`app-admin-banner`, in the app and the admin) says it and has the way back (`backToAdmin` only chooses the admin's own account; the page `/jigsaw` is opened). The account page of the app shows the level of the account that plays as a badge beside Active.

**Picking an account from a list** (the account page of the app) goes by one rule, `JigsawUserService.playAs`: an open account at once; a locked one with a login verified for it, **or an admin's login, which goes into it as the button on `/jigsaw` does** (never checked in the page alone: that refused an admin the server allows); else the login page or "locked to other sign-ins".

**6. What the page does with a refusal.** `401 logon-required` and `403 wrong-logon` go to `LogonRequired`: the person stops playing as that account and is sent to `/login?notice=needlogin` or, when a login is signed in that is not the account's, to `/play/account?logon=wrong` ("This account is locked to other sign-ins"); somebody who is on the account page already stays there, and the reason is put in the address (`?logon=`), which `app-my-logon-users` shows (while a login is signed in). So that message after an action on **another** account means the server did not accept the login for **that** account: for an admin action it means the account that acts is not (yet) a real admin.

**Why it cannot leak** (each is tested in `user-levels.test.ts`, "an admin's login cannot leak", and the same chain on the real Firestore in `test-emulator/stores.emulator.test.ts`):
- The only input is the **verified token**. Nothing the client says about itself (no header such as `X-Jigsaw-Admin` or `X-Jigsaw-Level`, no body field) makes a call an admin's; the headers of old are not known any more.
- **Nothing is kept.** Whether a login is an admin's is asked of the database at every call that carries a login (`gate.ts`, `isAdminLogin`), so a demoted admin, or a login taken off an admin account, is refused at once, also by another instance of the function. (The accounts' own logins are kept 10 seconds as before; that is for the account's use, not for admin rights.)
- **Never on a failure:** if the database cannot answer, the call fails with 503; a bad or missing token is 401; a good token that is no admin's is 403.
- **The admin flag lives for one call.** It is an `AsyncLocalStorage` of that call: another call, at the same moment or after, cannot see it, and it is never written to an account, a cache or a document (`Levels.of` does not keep an answer given for it).
- An account with no verified login has no level, so no login can be made an admin by writing a level on an open account; an account that loses its last login loses its level.
- The logins of an account (add, remove, link codes) are never opened by an admin login, so an admin login cannot be added to another account through this.

**Where each is tested:** `functions/test/logons.test.ts`, `user-logons.test.ts` (the gate and the logins), `user-levels.test.ts` (levels, the first admin, admin rights, going into an account, the front page), `round-privacy.test.ts` (rounds), `functions/test-emulator/stores.emulator.test.ts` (the same on the real Firestore, `npm run test:emulator`).

- **A new person only says their name** (the account page of the app, `/play/account`, `play/pages/account/`: somebody who is not signed in sees the accounts to choose from, and **Make my own account** asks "What is your name?", one field and the button "Start playing"; `JigsawUserService.createFromName` makes the user with a user name worked out from the name, `JigsawUsers.usernameFrom(name, digits)`: the plain name first, four digits added only when the server answers 409 (taken), never for another error (a taken user name makes nothing: `createFromName` says which user name, `lookup` reads that user and the page asks). When somebody already has it (what was typed is the whole name, the whole user name or a whole word of either, in any case and ignoring accents: `JigsawUsers.matches`, two letters at least, so "leif" finds "Leif Auke" and `leif-auke-5`; or it is the user name the typed name would make) the page first asks "Is that you?" (`sameUsers` of the page, a list to choose from when several have the name): "Yes, that is me" plays as that user, "No, make a new account" makes one with digits). A signed-in person has the box of the accounts of the login first (and makes a new account there), with **Show other accounts** for the list. The user name and the rest are changed afterwards, in the edit form.
- **Signing in with Firebase** (`functions/src/logons/` and `frontend/src/app/logons/`: **everything about it is in these two folders**, beside the users of the jigsaw above, which still work as before: `X-Jigsaw-User` and the account page; a user can be verified by Firebase logins, see the last section of this file). The project is shared with Seven Friends, so a Firebase login is one login for both apps and the account is the same document, `user-account/<Firebase UID>`. `POST /jigsaw/api/session` (the page sends `Authorization: Bearer <ID token>` after it has signed in) checks the token (`require-auth.ts`: `verifyIdToken` and the look-up of a deleted login, as Seven Friends does) and makes or updates that document (`account-store.ts`, one transaction): `uid`, `email`, `emailLower`, `emailVerified`, `verifiedPhone`, `phoneKey`, `phone`, `displayName` (a name that is there stays; the login's name is only the start), `photoURL`, `provider`, the stamp `accountId` (made once, never changed), `lastLoginAt`, `loginCount` and `createdAt`. What Seven Friends keeps in the same document (profile, circles, medals, setup) is left as it is, and no circle is made here: Seven Friends makes it when the person opens it. The rules are on the model `LogonAccounts` (`models/shared/logon.ts`: `stored`, `publicOf`; tested in `functions/test/logons.test.ts` with a fake verifier, no call to Firebase). **Frontend:** `logons/firebase.ts` (the Auth emulator is on port 9109), `auth.service.ts` (Google, email and password, the emailed link; every way ends in `finishLogin`, which calls the session route and signs out again when that fails), `auth-errors.ts`, `auth.guard.ts` (`guestGuard`: somebody signed in does not need the login pages and goes to `/play/account`), the pages at the **top level**: `/login`, `/login/email` (ask for the link), `/login/link` (the page the link opens), each framed by `logon-shell.ts` (`logons.routes.ts`). There is no entry for the login page in the menu: a person gets to it from the account page (a locked account that is picked; **Lock this account** and **Use another sign-in** in the Sign-ins of the edit form; **Use another sign-in** in the box of a signed-in login). **Who is signed in, and Sign out, are on the account page**: the line "Signed in as …" (in the box of the accounts of the login, and in the Sign-ins of an account that is not locked yet) has a **Sign out**, and the **Sign out** at the top of the account that plays lets the account go, signs the login out too and goes home. Texts: the scope `logons` in the nine languages (the Seven Friends translations reused). Not built: phone (SMS), the page that finishes a verification email (the project has one template for both apps, so such a link opens Seven Friends' page first), native Google sign-in in the Android app, and a login that is needed for any call of the API except for a user that has verified logins. The users that existed need no move: they have no verified login and are used as before.
- **Language:** the languages are one list, `JIGSAW_LANGUAGES` (`models/shared/language.ts`: en, nb, sv, da, fi, de, fr, es, nl; `JigsawLanguages.is/of/nameOf`; the app's `LANGUAGES` is that list). **A user has a `language`** (English until chosen; set in the edit form on the account page, made or changed with `language` on `POST`/`PUT /jigsaw/api/jigsaw-users`; `JigsawUserService` shows the app in the language of the user when the user is chosen or read, and a language chosen in a menu or in the preferences is kept as the user's, `changeLanguage`). **A jigsaw has an optional `language`** (what its name and description are written in; English when it says nothing: `JigsawLanguages.of`): the form of a new picture starts it as the language the app is shown in (the user's), and the form changes it, also for a picture that has been played (it is not one of the things every round shares). It is kept for finding (`language` in `JigsawIndex`) and can be searched (`languages`, a list, in the filter).
- **A jigsaw user verified by Firebase logins** (`functions/src/logons/`: `gate.ts`, `link.ts`, `link-codes.ts`, `account-directory.ts`; the model is `JigsawUsers` in `models/shared/jigsaw-user.ts`, and `LinkCodes` and `LogonAccounts.label` in `logon.ts`; frontend `frontend/src/app/logons/`: `auth-token.interceptor.ts`, `logon-required.service.ts`, `logon-landing.ts`, `logons.service.ts`, `user-logins/`, `my-logon-users/`). **The rule:** a jigsaw user has `firebaseUids`, the list of the Firebase accounts verified for it, **at most 7** (`LOGONS_MAX`). A user with none is used with no login, exactly as before (all the users that existed are like that); one with some is used only by somebody signed in with one of them. **Any one is enough**: the person is signed in with one account at a time, and one account can be verified for several users. The list is **server only**: never in what the API tells the page (`JigsawUsers.publicOf` says `protected: true` instead; `ownerView` keeps the e-mail for whoever made the user), never set by a body from the page (only the logon routes change it). **The gate** (`createGate`, in front of the whole API in `createJigsawApp`) reads the token that comes with every call (the page adds `Authorization: Bearer` to each call of the API when somebody is signed in, `authTokenInterceptor`) and the user the call acts as: the header `X-Jigsaw-User` and, for the routes of one user (`/jigsaw-users/:id/...`), the user in the address. A user with no verified account ignores the token (a bad one too). For one with accounts, no token or a bad one is **401 `logon-required`**, a good token for an account that is not one of them is **403 `wrong-logon`**, and a question that cannot be answered (Firebase is not there) is **503** and never a way through. Not gated: `/health`, `/session`, making a user, the list of users, a user by user name or by id, and `POST .../logons/redeem`. A user is kept in memory for 10 s. **Accounts that are gone:** an account deleted in Firebase (Seven Friends' Delete my account does it) is taken from the lists when it is found out (`AccountDirectory.gone`, one batch, asked at most once a minute for a user and once a minute for the list of users); a user whose every account is gone is **open again**, with everything it has; when Firebase cannot be asked nobody is freed. **The routes** (`link.ts`, `/jigsaw-users/:id/logons`, each needs a login signed in): `GET` the verified logins as `{ref, you, provider, name, email, phone, photoURL}` (what says which login it is is read from `user-account` when it is shown and never stored: the kind, the name, the full e-mail address, a phone number with only its last four digits, and the picture, which is only ever an https address (`LogonAccounts.shown`); `ref` is a short hash of the uid, so the page never has the accounts' own ids); `PUT` verifies the account that is signed in for the user (for a user with none: whoever acts as it may); `POST /codes` makes a **link code** (ten letters and digits shown as `ABCDE-FGHJK`, valid `LinkCodes.MINUTES` = 10 minutes, one at a time for a user, only its hash is kept, in `jigsaw-users/<id>/logon-codes`); `POST /redeem {code}` (typed on the second login, which is not verified yet; works once; ten wrong codes make it wait for 10 minutes: 429); `DELETE /:ref` takes one login away (any verified login may; the last one makes the user open again); the eighth login is refused (409). `POST /jigsaw-users` with `linkLogon: true` makes a user that is verified for the account signed in (the uid is from the token, never from the body). `POST /session` and `GET /session` say which users the account is verified for (`UserStore.linkedTo`: one `array-contains`, no index). **Frontend:** a `logon-required` or `wrong-logon` answer is told to `LogonRequired`, which has the person stop playing as that user and sends them to `/login?notice=needlogin` (nobody signed in) or to `/play/account?logon=wrong` (another login). After a login `LogonLanding` keeps the user who plays, else plays as the only user the login is verified for, else goes to `/play/account` (which goes on to `?next=` once somebody plays, only for a picture's page or a page of the admin). **The list of users** on the account page leaves out the users the signed-in login is verified for: they are in the box above it (`app-my-logon-users`), so the list is the users the person has no access to yet. **Deleting a user and making one:** in `app-my-logon-users` each user of the login has a trash button, and Make a new user with my login asks first (it shows the name and the user name it would get, and says when the user name is taken so digits are added). `DELETE /jigsaw-users/:id` (`JigsawUsers.removeError`, `UserUse` in `jigsaw-users.ts`) works only when nothing is attached: no jigsaw the user owns, no round it has played and no login besides the one that asks (an opened round nobody moved a piece in is taken away with it); otherwise 409 with the reason. The gate lets only a login of the user do it. **Choosing a user the person is not verified for:** the account page asks `JigsawUserService.playAs`, which checks **before it switches**: a protected user is played as only when a login is signed in and the users that login is verified for (`AuthService.linked`, read again at that moment) include it, or the login is an admin's; otherwise nothing is switched: with nobody signed in the person goes to the login page (`notice=needlogin`, and back), and with a login that may not, the page says why in a box over the list (`blocked`: locked to other sign-ins; sign in with the right one, or use a **link code**: it works once, for `LinkCodes.MINUTES` minutes; the person opens **More** in the box of the accounts, presses "I have a link code" and types the user name and the code). A call that the gate turns down while the person is on the account page releases the user and says the same through `?logon=wrong` or `?logon=needlogin`, which `app-my-logon-users` reads as the address changes (it is shown while a login is signed in). **Another login:** where a user is not verified for the login that is signed in, the person is asked to verify it with the current login (**Lock this account with my sign-in**) or to **Use another sign-in** (`LogonLanding.switchLogin`: the login is signed out and the person goes to the login page; for a user with no login yet the next login is verified for it); the same Use another sign-in is in `app-my-logon-users` (under More). **Signing in to protect a user:** **Lock this account** (shown in the edit form when nobody is signed in) notes the wish (`LogonLanding.intend`, kept in `localStorage` as `jigsaw.protectAfterLogin` for 30 minutes, and used once); when the login is done, `LogonLanding.go` verifies that login for the user who plays **if it is the user the wish was for** (so a link from outside cannot make a login verified for another user) and nothing protects it yet, and takes the person to the account page, where the list of the logins is. Without that wish, signing in only signs in, and the button Lock this account with my sign-in does the verifying. The **edit form of the user** (just there on the account page while an account plays) is Who you are (user name, name, picture, language) and then **Sign-ins**, with no Save (it has no field for the e-mail); the section Sign-ins: `app-user-logins` shows the list of the verified logins (the picture of the account, or an icon for the kind of login: Google, e-mail, phone; the name in bold with the e-mail address under it; "This login" on the one that is signed in) with Add another sign-in (the code is shown with a Copy button) and Remove (asked first; the last one warns that the user will be open again); its buttons do not save or close the form. `app-my-logon-users` (what the login that is signed in can do: play as one of its users, make a new user with it, or use a link code with a user name) is at the top of the choosing of a user, for a signed-in person, where a person has no user yet; a protected user has a lock in the list. For a user with no verified login, a private or hidden jigsaw is a way of not showing, not a lock (the server only sees an id in `X-Jigsaw-User`); for one with logins it is a lock, since the gate decides who acts as the user.

**The accounts are listed with the one used last first.** `JigsawUserSpec.lastUsedAt` is written by `POST /jigsaw-users/:id/used` when an account is chosen (`JigsawUserService.choose`; at most once a minute, `JigsawUsers.USED_KEEP_MS`; never from a body of the page), and the list on the account page sorts with `JigsawUsers.byLastUsed` (used last, then never used newest made first, then by name).

**The picture of an account.** In the edit form of the account page the person chooses a file; the page cuts the middle of it square and shrinks it to at most 128 × 128 pixels as a JPEG (`jigsaw/account-picture.ts`) and sends it with the change (`picture`, a data address, or `null` to take it away; `JigsawUsers.pictureError` checks it). The server keeps it as a **file in Storage** (`jigsaw/accounts/<id>/picture`, the same `ImageStore` as the pictures of the jigsaws, `storageImageStore(root)`), checks the bytes really are a JPEG, and keeps only **when** it was set (`pictureAt`) on the account; a lists of accounts and the session tell `pictureAt`, never the picture. The picture is read at `GET /jigsaw-users/:id/picture?v=<pictureAt>` (open like the name, because an image in a list cannot carry a token; the gate lets it through), and `app-account-avatar` shows it (the icon when there is none). Deleting the account deletes the file.

- **A picture can be looked at with no account; an account is asked for only to start or enter a round, or to make or change a picture.** With nobody who plays, the page before the puzzle (`/play/round/:id`) shows the picture, its facts and the rounds, with **Logon** in place of the start (to `/play/account?next=` that page, and back as soon as somebody plays), the puzzle (`/play/jigsaw/:id`) goes to that page, the hearts are not shown, a kept filter with favorites in it is looked for without them (`listQuestion`), and the menus have Logon.

- **Looking needs no login, even for an account that needs one** (the gate, `looking()` in `functions/src/logons/gate.ts`): a read that is not about the user (the list of jigsaws, the search, a jigsaw, its picture, the rounds of a jigsaw) from an account that needs a login and is not signed in is answered for nobody (the header `X-Jigsaw-User` is taken off, so that account's private jigsaws stay private) and no login is asked for. What is the user's own (`/jigsaw-users/:id/...`, favorites, "your jigsaws" `/jigsaw-search/mine`), **opening a round** (`GET /jigsaw/:id/plays/:playId`) and every change still answer 401 `logon-required` (and the page goes to the sign-in, `LogonRequired`). On the page, `JigsawUserService.acting` is the user only while nothing more is needed (an account that needs a login only while somebody is signed in with one of its logins); hearts, the rounds band, "mine" and every change go by `acting`, not by `user`. With only a locked account chosen that nobody is signed in for, the page before the puzzle offers Logon, as for nobody.

- **The edit form of the account saves by itself, and a login that was started to lock it ends at it:** the edit form on the account page has no Save and no Close: every change (name, user name, picture, language) is saved 0.8 s after the last one (`AccountEdit` in `app/jigsaw/account-edit.ts`; nothing is saved while the name is empty or a new user name has not been looked up and found free), and what is waiting is saved when the page is left. A login that is started from the Sign-ins of the edit form (lock this account, or use another sign-in) ends at the account page (`LogonLanding`): also when the login could not be verified or the user is protected already.

- **Levels: user, publisher, admin** (`models/shared/user-level.ts`: `UserLevels`; server `functions/src/jigsaw/user-levels.ts`; pages `frontend/src/app/admin/`: `account-levels/`, `admin.guard.ts`). A jigsaw user has an optional `level` (`user` when nothing is kept; the document keeps it only for publisher and admin). **What each may do:** a `user` plays and makes private or hidden jigsaws and pictures; a `publisher` can also make them **public** (a jigsaw that is public already may stay public, so its owner can still change its name: `UserLevels.publishError`, checked on `POST /jigsaw` and `PUT /jigsaw/:id`, 403, after the owner check so it says nothing about a jigsaw the person may not see); an `admin` can do that too, **change and delete any jigsaw and any round** (`ownerOnly` and `ownRound` take an admin), **open the private and hidden jigsaws of others by their address** (`canSee` takes an admin; the admin does not find them on the home page, in the search or the lists, only their own: `canFind`; a **publisher cannot** open them, and neither can a user: for them it is 404), start a round on a private one, **change and delete the accounts of others** (the gate lets an admin's login through for `PUT` and `DELETE /jigsaw-users/:id`: `managesAccount`; the logins of another account are still its own, and an account that owns jigsaws, or the last admin, is not deleted) and **set the level of every account**. **Private and hidden jigsaws, and their pictures, stay with their owner (and the players of a private one) for an admin too**: `canSee` has no admin in it, an admin gets 404 for them and cannot change or delete them. **A level counts only for an account that needs a login** (`UserLevels.of`: the level kept, but `user` for an account with no verified Firebase login): the header `X-Jigsaw-User` is not a lock for such an account, so anybody who knew the id of an admin could be one; for a protected one the gate has seen that the login may act as it. **An account with no verified login can never be more than a user:** it cannot be given a higher level (`UserLevels.setError`, 409), the level of one is ignored anyway (`UserLevels.of`), and an account that loses its last login (it is open again) loses its level too, so the next login to verify it does not find one. **Setting it:** `PUT /jigsaw-levels/:id {level}` (an admin only, 403 otherwise, **except while there is no admin at all** (no account that counts as one: `UserLevels.hasAdmin`): then any account that exists may, so the first admin can be made from the page (the account that gets a level above `user` must still have a verified login, 409), and `GET /jigsaw-levels/open` says `{ open: true }`; 400 for a level that does not exist, 404 for an account that does not exist, 409 when the last admin steps down). It is not under `/jigsaw-users/:id` on purpose: the gate then asks for the login of the admin who asks, not for the login of the account that is changed. The level is **never set by a body that makes or changes an account** (`JigsawUsers.stored`/`change` do not know it) and is told to the page in the account (`level`, with `protected`), so the page can show or hide: `JigsawUserService.level/mayPublish/isAdmin` (what the page shows only: the server decides), the **Admin** entry of the app's account menu and the page `/jigsaw` (`adminGuard`, `mayOpenLevels`) are for an admin (for every account who plays while there is no admin: `JigsawUserService.noAdmin`, asked in `load()` and after a level is set); a visitor who is not logged on is sent to `/play/account?next=...` and back, an account that may not goes home. For an admin the page also has Edit (name, alias), Delete and the way into each account, and the page of a picture lets its owner and an admin change and delete it. **What the page hides by level** (it only shows; the server decides): the Public choice is not shown to one who cannot publish (the rows and the buttons for the ticked pictures in My pictures, and the pills of `app-visibility-choice` on the forms; what is public already still shows it); **AI use** is a page of the admin, `/jigsaw/ai-use` (`ai-use/`, what the AI has used for the account, for an admin only: `adminOnlyGuard`; the route `/jigsaw-users/:id/token-usage` itself is not restricted by level yet). **An admin acts as any account** with only the admin's own login: see section 5 at the top of this file. A level is read for a call at most every 10 s (`userLevels`). **The first admin** is made from the page `/jigsaw` while there is no admin at all (section 4 at the top of this file); nothing is set by hand in Firestore. Tests: `functions/test/user-levels.test.ts`; the other tests of the API pass `levels: PUBLISHER` (`memory-plays.ts`) so a test can make a public jigsaw as anybody.

**The sign-in address.** `authDomain` in `frontend/src/environments/environment.ts` is `karins-jigsaw.web.app`, **the site's own address** (Firebase Hosting serves the sign-in handler at `/__/auth/handler` on every site it hosts), and the Google sign-in window says "to continue to" that address. It must stay the same as the address people open: a browser on a phone or pad may block the way back from the handler of another address (it was `sevenfriends.io`, and Google sign-in was then blocked on a pad after the account was chosen). It needs `https://karins-jigsaw.web.app/__/auth/handler` among the Authorised redirect URIs of the project's Web client (Google Cloud console > APIs & Services > Credentials) and `karins-jigsaw.web.app` among the Authorised domains (Firebase console > Authentication > Settings); these are changes in the shared project, made by hand, never from here, and they are added to what is there, nothing is removed. Without the redirect URI Google sign-in fails for everybody with a redirect error: add it BEFORE deploying a change of this address.

- **A login comes back to where it was started.** The buttons that go to the login page (Lock this account, Use another sign-in, Sign in) ask `LogonLanding` where the person is (`here()`, `accountPage()`: the account page, `/play/account`); `LogonRequired` sends the person to the login page with the page they were on as `next` when the server asks for a login.

## Limits of an account that is not verified
**An account with no verified login:**
1. **cannot add packages** (neither Add to my pictures nor Buy);
2. **can have at most 5 uploaded pictures** (`UNVERIFIED_PICTURES_MAX`): the pictures and ready jigsaws it owns now, so deleting one makes room;
3. **can still play the pictures that are publicly available**: the limits take nothing away from playing.

What an account already has stays (more pictures, packages added before): only new ones are stopped. **An admin is not stopped**, also when doing it for an account.

The rule is `AccountLimits` (`models/shared/account-limits.ts`). The API asks it: `PUT /jigsaw-users/:id/bought-packages/:packageId` (403), `POST /jigsaw` and a `PUT /jigsaw/:id` that gives a jigsaw to another owner (403; the count is `countOwned` of the jigsaw store, a Firestore count on `ownerUid`). The pages say why before the person tries: `app-upload-limit` over the Save button of the form of a new picture or ready jigsaw (how many are used, and with 5 the Save buttons are off), and the page of a package has **Verify your account to add packages** in place of the button.

**A verified user who is no publisher** has at most 20 pictures that are not public (`PRIVATE_PICTURES_MAX`: private and hidden together, since they can make no other kind), refused with 403 on `POST /jigsaw` (and when a picture is given to them); publishers and admins have no limit; the add forms say how many are used.

# Users, signing in with Firebase, and language

Part of the project guide (moved out of `CLAUDE.md`; text unchanged). Read this before changing this area.

- **A new person only says their name** (`/jigsaw/user` starts in mode `start`: the title is "What is your name?", one field and the button "Start playing"; `JigsawUserService.createFromName` makes the user with a user name worked out from the name, `JigsawUsers.usernameFrom(name, digits)`: the plain name first, four digits added only when the server answers 409 (taken), never for another error (a taken user name makes nothing: `createFromName` says which user name, `lookup` reads that user and the page asks). When somebody already has it (what was typed is the whole name, the whole user name or a whole word of either, in any case and ignoring accents: `JigsawUsers.matches`, two letters at least, so "leif" finds "Leif Auke" and `leif-auke-5`; or it is the user name the typed name would make) the page first asks "Is that you?" (`JigsawUser.sameUsers`, a list to choose from when several have the name): "Yes, that is me" plays as that user, "No, make a new user" makes one with digits). The list of the users is behind "I have played before" (so nobody presses a name that is not theirs) and the whole form (user name, language, e-mail) behind "Choose my own user name".
- **Signing in with Firebase** (`functions/src/logons/` and `frontend/src/app/logons/`: **everything about it is in these two folders**, beside the users of the jigsaw above, which still work as before: `X-Jigsaw-User`, `userGuard` and `/jigsaw/user`; a user can be verified by Firebase logins, see the last section of this file). The project is shared with Seven Friends, so a Firebase login is one login for both apps and the account is the same document, `user-account/<Firebase UID>`. `POST /jigsaw/api/session` (the page sends `Authorization: Bearer <ID token>` after it has signed in) checks the token (`require-auth.ts`: `verifyIdToken` and the look-up of a deleted login, as Seven Friends does) and makes or updates that document (`account-store.ts`, one transaction): `uid`, `email`, `emailLower`, `emailVerified`, `verifiedPhone`, `phoneKey`, `phone`, `displayName` (a name that is there stays; the login's name is only the start), `photoURL`, `provider`, the stamp `accountId` (made once, never changed), `lastLoginAt`, `loginCount` and `createdAt`. What Seven Friends keeps in the same document (profile, circles, medals, setup) is left as it is, and no circle is made here: Seven Friends makes it when the person opens it. The rules are on the model `LogonAccounts` (`models/shared/logon.ts`: `stored`, `publicOf`; tested in `functions/test/logons.test.ts` with a fake verifier, no call to Firebase). **Frontend:** `logons/firebase.ts` (the Auth emulator is on port 9109), `auth.service.ts` (Google, email and password, the emailed link; every way ends in `finishLogin`, which calls the session route and signs out again when that fails), `auth-errors.ts`, `auth.guard.ts` (`authGuard` with `?next=`, `guestGuard`), the pages at the **top level**: `/login`, `/login/email` (ask for the link), `/login/link` (the page the link opens), `/account` (who is signed in, Sign out; behind `authGuard`), all inside `JigsawShell` (`logons.routes.ts`). There is no entry for it in the menu: a person gets to the login page from the user page ("Sign in to protect this user", "Have a login? Sign in", "Sign in with another login"), and the **Log out** of the user page (it lets the user go and signs the login out too), and the line that says who is signed in ("Signed in as …", in the box at the top of the choosing of a user and in the Logins section of the edit form) has a **Sign out**; `/account` (who is signed in, Sign out) is also opened by its address. Texts: the scope `logons` in the nine languages (the Seven Friends translations reused). Not built: phone (SMS), the page that finishes a verification email (the project has one template for both apps, so such a link opens Seven Friends' page first), native Google sign-in in the Android app, and a login that is needed for any call of the API except for a user that has verified logins. The users that existed need no move: they have no verified login and are used as before.
- **Language:** the languages are one list, `JIGSAW_LANGUAGES` (`models/shared/language.ts`: en, nb, sv, da, fi, de, fr, es, nl; `JigsawLanguages.is/of/nameOf`; the app's `LANGUAGES` is that list). **A user has a `language`** (English until chosen; set in the form on `/jigsaw/user`, made or changed with `language` on `POST`/`PUT /jigsaw/api/jigsaw-users`; `JigsawUserService` shows the app in the language of the user when the user is chosen or read, and a language chosen in the menu is kept as the user's, `changeLanguage`). **A jigsaw has an optional `language`** (what its name and description are written in; English when it says nothing: `JigsawLanguages.of`): the form of a new jigsaw starts it as the language the app is shown in (the user's), and the form of an edit and the edit panel of a played jigsaw change it (it is not one of the things every round shares). It is kept for finding (`language` in `JigsawIndex`) and can be searched (`languages`, a list, in the filter).
- **A jigsaw user verified by Firebase logins** (`functions/src/logons/`: `gate.ts`, `link.ts`, `link-codes.ts`, `account-directory.ts`; the model is `JigsawUsers` in `models/shared/jigsaw-user.ts`, and `LinkCodes` and `LogonAccounts.label` in `logon.ts`; frontend `frontend/src/app/logons/`: `auth-token.interceptor.ts`, `logon-required.service.ts`, `logon-landing.ts`, `logons.service.ts`, `user-logins/`, `my-logon-users/`). **The rule:** a jigsaw user has `firebaseUids`, the list of the Firebase accounts verified for it, **at most 7** (`LOGONS_MAX`). A user with none is used with no login, exactly as before (all the users that existed are like that); one with some is used only by somebody signed in with one of them. **Any one is enough**: the person is signed in with one account at a time, and one account can be verified for several users. The list is **server only**: never in what the API tells the page (`JigsawUsers.publicOf` says `protected: true` instead; `ownerView` keeps the e-mail for whoever made the user), never set by a body from the page (only the logon routes change it). **The gate** (`createGate`, in front of the whole API in `createJigsawApp`) reads the token that comes with every call (the page adds `Authorization: Bearer` to each call of the API when somebody is signed in, `authTokenInterceptor`) and the user the call acts as: the header `X-Jigsaw-User` and, for the routes of one user (`/jigsaw-users/:id/...`), the user in the address. A user with no verified account ignores the token (a bad one too). For one with accounts, no token or a bad one is **401 `logon-required`**, a good token for an account that is not one of them is **403 `wrong-logon`**, and a question that cannot be answered (Firebase is not there) is **503** and never a way through. Not gated: `/health`, `/session`, making a user, the list of users, a user by user name or by id, and `POST .../logons/redeem`. A user is kept in memory for 10 s. **Accounts that are gone:** an account deleted in Firebase (Seven Friends' Delete my account does it) is taken from the lists when it is found out (`AccountDirectory.gone`, one batch, asked at most once a minute for a user and once a minute for the list of users); a user whose every account is gone is **open again**, with everything it has; when Firebase cannot be asked nobody is freed. **The routes** (`link.ts`, `/jigsaw-users/:id/logons`, each needs a login signed in): `GET` the verified logins as `{ref, you, provider, name, email, phone, photoURL}` (what says which login it is is read from `user-account` when it is shown and never stored: the kind, the name, the full e-mail address, a phone number with only its last four digits, and the picture, which is only ever an https address (`LogonAccounts.shown`); `ref` is a short hash of the uid, so the page never has the accounts' own ids); `PUT` verifies the account that is signed in for the user (for a user with none: whoever acts as it may); `POST /codes` makes a **link code** (ten letters and digits shown as `ABCDE-FGHJK`, valid `LinkCodes.MINUTES` = 10 minutes, one at a time for a user, only its hash is kept, in `jigsaw-users/<id>/logon-codes`); `POST /redeem {code}` (typed on the second login, which is not verified yet; works once; ten wrong codes make it wait for 10 minutes: 429); `DELETE /:ref` takes one login away (any verified login may; the last one makes the user open again); the eighth login is refused (409). `POST /jigsaw-users` with `linkLogon: true` makes a user that is verified for the account signed in (the uid is from the token, never from the body). `POST /session` and `GET /session` say which users the account is verified for (`UserStore.linkedTo`: one `array-contains`, no index). **Frontend:** a `logon-required` or `wrong-logon` answer is told to `LogonRequired`, which has the person stop playing as that user and sends them to `/login?notice=needlogin` (nobody signed in) or to `/jigsaw/user?logon=wrong` (another login). After a login `LogonLanding` keeps the user who plays, else plays as the only user the login is verified for, else goes to `/jigsaw/user`. **The list of users** (I have played before) leaves out the users the signed-in login is verified for: they are in the box above it (`app-my-logon-users`), so the list is the users the person has no access to yet. **Deleting a user and making one:** in `app-my-logon-users` each user of the login has a trash button, and Make a new user with my login asks first (it shows the name and the user name it would get, and says when the user name is taken so digits are added). `DELETE /jigsaw-users/:id` (`JigsawUsers.removeError`, `UserUse` in `jigsaw-users.ts`) works only when nothing is attached: no jigsaw the user owns, no round it has played and no login besides the one that asks (an opened round nobody moved a piece in is taken away with it); otherwise 409 with the reason. The gate lets only a login of the user do it. **Choosing a user the person is not verified for:** `JigsawUser.pick` checks **before it switches** (`mayPlayAs`): a protected user is played as only when a login is signed in and the users that login is verified for (`AuthService.linked`, read again at that moment) include it; otherwise nothing is switched, and the page says why in a box over the list (`blocked`): nobody is signed in ("needs a login"), or the login that is signed in is not verified for it ("protected by other logins"), with a Sign in button and a line that explains the **link code** (`jigsawUser.codeHowTo`: someone who can already play as the user makes it with Edit, Add another login; it works once, for `LinkCodes.MINUTES` minutes; the person presses "I have a link code" and types the user name, which the line shows, and the code). A call that the gate turns down while the person is on `/jigsaw/user` (the user they had is protected by other logins, say) releases the user and says the same through `?logon=wrong` or `?logon=needlogin`, which `app-my-logon-users` reads as the address changes. **Another login:** where a user is not verified for the login that is signed in, the person is asked to verify it with the current login (Protect this user with my login) or to **Sign in with another login** (`LogonLanding.switchLogin`: the login is signed out and the person goes to the login page; for a user with no login yet the next login is verified for it); the same Sign in with another login is in `app-my-logon-users`. **Signing in to protect a user:** "Sign in to protect this user" (shown in the edit form when nobody is signed in) notes the wish (`LogonLanding.intend`, kept in `localStorage` as `jigsaw.protectAfterLogin` for 30 minutes, and used once); when the login is done, `LogonLanding.go` verifies that login for the user who plays **if it is the user the wish was for** (so a link from outside cannot make a login verified for another user) and nothing protects it yet, and takes the person to the edit form at the list of the logins (`/jigsaw/user?logins=1`). Without that wish, signing in only signs in, and the button Protect this user with my login does the verifying. The **edit form of the user** (Edit on the user page) is Who you are, then **Logins**, then Contact, then Cancel and Save; the section Logins: `app-user-logins` shows the list of the verified logins (the picture of the account, or an icon for the kind of login: Google, e-mail, phone; the name in bold with the e-mail address under it; "This login" on the one that is signed in) with Protect this user with my login, Add another login (the code is shown with a Copy button), and Remove (asked first; the last one warns that the user will be open again); its buttons do not save or close the form. `app-my-logon-users` (what the login that is signed in can do: play as one of its users, make a new user with it, or use a link code with a user name) is at the top of the choosing of a user, where a person has no user yet; a protected user has a lock in the list. For a user with no verified login, a private or hidden jigsaw is a way of not showing, not a lock (the server only sees an id in `X-Jigsaw-User`); for one with logins it is a lock, since the gate decides who acts as the user.

**The accounts are listed with the one used last first.** `JigsawUserSpec.lastUsedAt` is written by `POST /jigsaw-users/:id/used` when an account is chosen (`JigsawUserService.choose`; at most once a minute, `JigsawUsers.USED_KEEP_MS`; never from a body of the page), and the list on the user page sorts with `JigsawUsers.byLastUsed` (used last, then never used newest made first, then by name).

**The picture of an account.** In the edit form (Edit account) the person chooses a file; the page cuts the middle of it square and shrinks it to at most 128 × 128 pixels as a JPEG (`jigsaw/account-picture.ts`) and sends it with the change (`picture`, a data address, or `null` to take it away; `JigsawUsers.pictureError` checks it). The server keeps it as a **file in Storage** (`jigsaw/accounts/<id>/picture`, the same `ImageStore` as the pictures of the jigsaws, `storageImageStore(root)`), checks the bytes really are a JPEG, and keeps only **when** it was set (`pictureAt`) on the account; a lists of accounts and the session tell `pictureAt`, never the picture. The picture is read at `GET /jigsaw-users/:id/picture?v=<pictureAt>` (open like the name, because an image in a list cannot carry a token; the gate lets it through), and `app-account-avatar` shows it (the icon when there is none). Deleting the account deletes the file.

- **A jigsaw can be looked at with no account; an account is asked for only to enter a round, or to make or edit a jigsaw** (`jigsaw.routes.ts`: `userGuard` is on `new`, `batch`, `:id/edit` and `:id/play/:playId`, not on `:id`). With nobody who plays: the page of a jigsaw shows it and everyone's rounds but nothing is "mine" (no Yours, no Delete, no Edit; `JigsawPage.mayChange` needs an account), the button to play sends the person to `/jigsaw/user?next=` the page of the jigsaw, the hearts, the quick filters Favorites and Solved and the "Mine / Others" choice of the list of rounds are not shown, and a kept search with favorites or solved in it is looked for without them (`JigsawFinder.load`).

- **Looking needs no login, even for an account that needs one** (the gate, `looking()` in `functions/src/logons/gate.ts`): a read that is not about the user (the list of jigsaws, the search, a jigsaw, its picture, the rounds of a jigsaw) from an account that needs a login and is not signed in is answered for nobody (the header `X-Jigsaw-User` is taken off, so that account's private jigsaws stay private) and no login is asked for. What is the user's own (`/jigsaw-users/:id/...`, favorites, "your jigsaws" `/jigsaw-search/mine`, the list of rounds `/jigsaw-rounds`), **opening a round** (`GET /jigsaw/:id/plays/:playId`) and every change still answer 401 `logon-required` (and the page goes to the sign-in, `LogonRequired`). On the page, `JigsawUserService.acting` is the user only while nothing more is needed (an account that needs a login only while somebody is signed in with one of its logins); hearts, the quick filters Favorites and Solved, the rounds band, "mine" and every change go by `acting`, not by `user`. The button to play with only a locked account chosen goes to `/login` and back.

- **The edit form of the account saves by itself, and a login always ends at it:** the form of Edit account has no Save: every change (name, user name, picture, language) is saved 0.8 s after the last one (`startEditAutosave` in `jigsaw-user.ts`; nothing is saved while the name is empty or a new user name has not been looked up and found free), and the button is Close, which saves what is waiting and closes the form (so does pressing Edit again). A login that is started from the edit form (the list of the logins in it: sign in to verify, or sign in with another login) always ends at the page of the user with the edit form open, at the list of the logins (`/jigsaw/user?logins=1`, `LogonLanding`): also when the login could not be verified or the user is protected already.

- **Levels: user, publisher, admin** (`models/shared/user-level.ts`: `UserLevels`; server `functions/src/jigsaw/user-levels.ts`; page `frontend/src/app/jigsaw/jigsaw-admin/`, `admin.guard.ts`). A jigsaw user has an optional `level` (`user` when nothing is kept; the document keeps it only for publisher and admin). **What each may do:** a `user` plays and makes private or hidden jigsaws and pictures; a `publisher` can also make them **public** (a jigsaw that is public already may stay public, so its owner can still change its name: `UserLevels.publishError`, checked on `POST /jigsaw` and `PUT /jigsaw/:id`, 403, after the owner check so it says nothing about a jigsaw the person may not see); an `admin` can do that too, **change and delete any jigsaw and any round** (`ownerOnly` and `ownRound` take an admin), **open the private and hidden jigsaws of others by their address** (`canSee` takes an admin; the admin does not find them in the front page, the search or the lists, only their own: `canFind`; a **publisher cannot** open them, and neither can a user: for them it is 404), start a round on a private one, **change and delete the accounts of others** (the gate lets an admin's login through for `PUT` and `DELETE /jigsaw-users/:id`: `managesAccount`; the logins of another account are still its own, and an account that owns jigsaws, or the last admin, is not deleted) and **set the level of every account**. **Private and hidden jigsaws, and their pictures, stay with their owner (and the players of a private one) for an admin too**: `canSee` has no admin in it, an admin gets 404 for them and cannot change or delete them. **A level counts only for an account that needs a login** (`UserLevels.of`: the level kept, but `user` for an account with no verified Firebase login): the header `X-Jigsaw-User` is not a lock for such an account, so anybody who knew the id of an admin could be one; for a protected one the gate has seen that the login may act as it. **An account with no verified login can never be more than a user:** it cannot be given a higher level (`UserLevels.setError`, 409), the level of one is ignored anyway (`UserLevels.of`), and an account that loses its last login (it is open again) loses its level too, so the next login to verify it does not find one. **Setting it:** `PUT /jigsaw-levels/:id {level}` (an admin only, 403 otherwise, **except while there is no admin at all** (no account that counts as one: `UserLevels.hasAdmin`): then any account that exists may, so the first admin can be made from the page (the account that gets a level above `user` must still have a verified login, 409), and `GET /jigsaw-levels/open` says `{ open: true }`; 400 for a level that does not exist, 404 for an account that does not exist, 409 when the last admin steps down). It is not under `/jigsaw-users/:id` on purpose: the gate then asks for the login of the admin who asks, not for the login of the account that is changed. The level is **never set by a body that makes or changes an account** (`JigsawUsers.stored`/`change` do not know it) and is told to the page in the account (`level`, with `protected`), so the page can show or hide: `JigsawUserService.level/mayPublish/isAdmin` (what the page shows only: the server decides), Public is disabled in `app-visibility-choice` and on the user page for one who cannot publish, the **Admin** link in the menu and the page `/jigsaw/admin` (`adminGuard`, `mayOpenLevels`) are for an admin (for every account who plays while there is no admin: `JigsawUserService.noAdmin`, asked in `load()` and after a level is set), and the page has Edit (name, alias) and Delete for every account, and the Edit and Delete buttons of a jigsaw are shown to its owner and to an admin. **What the page hides by level** (it only shows; the server decides): the Public choice is not shown to one who cannot publish (the rows and the buttons for the ticked jigsaws on the user page, and the pills on the forms; a row that is public already still shows what it is); the buttons **Make packages** and **AI use** in the row of tabs of the user page are links to pages of their own: `/jigsaw/packages/make` (a dummy, `make-packages/`, for a publisher or an admin: `publisherGuard`; see `TODO.md`) and `/jigsaw/ai-use` (`ai-use/`, what the AI has used for the account, for an admin only: `adminOnlyGuard`; the route `/jigsaw-users/:id/token-usage` itself is not restricted by level yet). **An admin goes into an account** (the button `bi-box-arrow-in-right` on `/jigsaw/admin`, `JigsawUserService.openAs`): the app is then that account, its jigsaws (private ones too), rounds and settings, seen and changed as it, with no login of its own. The page sends the header `X-Jigsaw-Admin` (the admin's id, kept for this tab only in `sessionStorage` as `jigsaw.adminInto`, set by `userHeaderInterceptor`) with the admin's own token, and the gate (`gate.ts`) lets that login act as the account in `X-Jigsaw-User` when the admin is a **real** admin (`UserLevels.of`: an account that needs a login, with the level) and the token is one of that admin's own logins; it never applies to the logins of the account (`/jigsaw-users/:id/logons`), which stay its own. **While inside, the admin has every right of an admin there** (also in an account that is only a user, and whatever login the account needs): the gate says so for the call (`res.locals.adminInto`), `intoAccount` (`user-levels.ts`) runs the rest of the call with it in an `AsyncLocalStorage`, and `Levels.of` says `admin` for that account during that call only, so the admin can make public jigsaws, see and change everything, change other accounts and set levels; the page shows the admin things too (`JigsawUserService.level` is `admin` while `admin()` is set). The jigsaws and rounds made are the account's. A warning bar over the page says so and has **Back to** the admin account (`backToAdmin`), choosing or leaving any account ends it (`keepAdmin(null)`), and the account is not marked as used. Tests: `user-levels.test.ts`, "an admin going into an account". A level is read for a call at most every 10 s (`userLevels`). **The first admin** is set by hand: in Firestore, `jigsaw-users/<id>`, add `level: "admin"` to an account that has a verified login (the accounts that exist are all `user` until then, and so cannot make public jigsaws). Tests: `functions/test/user-levels.test.ts`; the other tests of the API pass `levels: PUBLISHER` (`memory-plays.ts`) so a test can make a public jigsaw as anybody.

**The sign-in address.** The Google sign-in window says "to continue to <authDomain>". `authDomain` in `frontend/src/environments/environment.ts` is `sevenfriends.io` (Seven Friends' own address, the same people and the same project; Firebase Hosting serves the sign-in handler at `/__/auth/handler` on every domain it hosts), not the project's `sevenfriends.firebaseapp.com`. This needs `https://sevenfriends.io/__/auth/handler` among the Authorised redirect URIs of the project's Web client (Google Cloud console > APIs & Services > Credentials), and `sevenfriends.io` and `karins-jigsaw.web.app` among the Authorised domains (Firebase console > Authentication > Settings); these are changes in the shared project, made by hand, never from here. Until the redirect URI is added, Google sign-in fails with a redirect error: add it BEFORE deploying this.
